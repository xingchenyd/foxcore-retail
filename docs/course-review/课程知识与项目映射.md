# 课程知识与 Foxcore Retail 项目映射

编写日期：2026-10-24。本文把《课程总结》的业务建模、需求、分析、设计四部分逐项落实到 Foxcore Retail，并依据当前 SQL 迁移、服务端代码、用例登记和修复决策区分「已实现的机制」「建议的目标」「尚未验证的结果」。本文不取代现有 UC-01—UC-13 编号，也不把参考文档中的内容视为用户新增指令。

## 1. 证据边界与项目定位

本项目是展会、市集等现场活动零售的教学实现，核心业务是：活动与展位准备、人员排班、备货、协商价销售、线下收款登记、退货退款登记、佣金结算和统计分析。系统用户为 OWNER 和 SALESPERSON；顾客在线下购买、付款或退货，没有顾客账号，也没有直接操作本系统的入口。

本次资料依据包括：用户提供的《课程总结》、Quickbooks 1.0 ERD 和 Shopify ERD；仓库的 `docs/01-vision-business.md`、`docs/02-SRS.md`、`docs/03-SDD.md`、`docs/use-cases.json`、`docs/fixes/decisions.md`；`db/migrations/001_core.sql`；当前 `catalog.ts`、`catalog-updates.ts`、`sales.ts`、`returns.ts`、`return-target.ts`、`inventory.ts`、`commissions.ts`、`core.ts`、`db.ts` 等代码。原 Foxcore A/B 案例内容在本节沿用仓库的来源标记，没有据此声称本次重新完成原案例全部页的逐字核验。

资料标签统一如下：CASE 表示仓库注明的案例要求；DERIVED 表示由痛点推导的需求；EXT 表示系统运行所需的补充；DEC 表示项目自行选择的规则；PROPOSED 表示本文建议、尚未因此自动成为已实现功能。代码存在只能证明实现入口存在，测试文件存在只能证明有测试设计，均不等于本轮执行通过。

当前范围明确为单货币 CAD、业务时区 America/Toronto、主仓 MAIN 与展位库位、线下现金或独立支付终端。资金由线下渠道执行，系统记录事实与参考号。采购供应商、顾客会员、线上商城、支付网关、在途物流和总账会计不在当前实现范围。

## 2. A：业务建模

### 2.1 愿景应由关键涉众驱动，并能测量

建议愿景：让现场销售在可追溯的活动、展位和班次内完成核价、占库和收款登记，使管理员可以解释每一笔销售、每一件库存变化和每一笔佣金。

下表是建议验收目标，全部不是本次实测业绩。现有仓库中的「秒级」「零争议」「100% 录入」也只能作为目标，不能在缺少统计证据时写成既成效果。

| 涉众 | 核心利益 | 建议测量方式与目标 | 当前证据边界 |
|---|---|---|---|
| 经营者 / OWNER | 不漏账、可解释毛利、佣金不重复支付 | 已过账单据的归属链、快照和审计完整率目标 100%；账面库存与流水差额目标 0 | 已有归属复合外键、快照、审计与核查 SQL；仍需实际运行证据 |
| 销售顾问 | 录入方便、本人归属清楚、佣金透明 | 观察真实用户完成典型三行销售的任务成功率；建议目标 ≥95%，首轮计时先建立基线 | 未开展现场可用性观察，不能伪造完成时长 |
| 顾客 | 金额正确、退款清楚 | 同一原行全部退完时，退款净额、税额与原成交对应金额一致；超退拒绝率目标 100% | 有累计差额分摊与限量逻辑；实际业务数据尚需核对 |
| 管理者 / 财务核对人员 | 能解释未结佣金和退款 | 每笔结算能回溯其销售正项、退货负项与线下支付凭证 | 有流水、认领、结算表；无银行自动对账 |
| 运维人员 | 可恢复、可迁移、权限可控 | 按项目确定的 RPO/RTO 演练备份恢复；建议先以每日备份、30 分钟恢复作为评审目标 | 目标须结合真实规模确认；脚本存在不代表恢复演练成功 |
| 教师 / 评审 | 方法完整、图文和代码一致 | 每个核心用例能追踪到规约、图、代码、表和验证结果 | 旧 PDF 和图形存在版本差异，应以本轮生成材料及代码核对 |

### 2.2 业务用例与系统用例不是同一层次

业务用例围绕组织提供的价值：向顾客完成现场销售、向顾客处理售后、向销售顾问核算报酬、为经营者形成活动经营信息。管理员和销售顾问在这些业务过程中是业务工人，商品、销售单、库存记录、佣金记录是业务实体。

系统用例围绕软件提供的价值：管理活动与展位、维护主数据、排班开关班、收货调拨盘点、录入草稿、准备收款、确认成交、核对取消、退货更正、佣金结算、查询导出、账户审计、身份认证。系统用例图的直接执行者是 OWNER 和 SALESPERSON。顾客和外部终端可以出现在业务上下文图、业务序列图中；当前没有直接 API 交互，不能在系统用例图上画成直接点击系统的角色。

### 2.3 AS-IS：描述来源事实，明确尚未验证的假设

仓库将纸笔录单、人工转抄、库存估计和佣金争议列为案例背景。按照课程要求，AS-IS 应来自真实业务调查。本文只把它们作为「仓库案例叙述的现状模型」，不声称已经访谈企业、旁观真实展会或测量漏记比例。尤其「退货时划改原单」「人工汇总耗时数天」等细节需要能够追溯到案例页码或调查记录，否则应标为待核实场景。

AS-IS 业务序列可组织为：顾客选购与议价 → 销售顾问核价并手写单据 → 顾客通过现金 / 外部终端付款 → 销售顾问标注付款与交货 → 管理员收单转抄 → 管理员汇总库存与佣金。图中应明确业务工人、实体和线下交接，不能把还未开发的控制器放进现状业务图。

### 2.4 TO-BE：信息自动化不等于取消真实物流

改进蓝图为：管理员确认活动规则、排班与备货 → 销售顾问建立草稿 → 系统检查有效班次、底价、税率、佣金率与可售量，并固化快照和占用 → 顾客线下付款 → 销售顾问登记已收款事实 → 系统原子更新销售、库存、佣金和审计 → 管理员核对例外并闭场。

课程中的「物流变成信息流」在本项目体现为交接单与业务状态可传递、可查询，不表示商品可以不进行实物交接。现有调拨必须在真实交接后提交 `handoverConfirmed=true`，资金同样需要线下完成。系统可以自动化核价、占库、归属、计税和佣金；商品交付、现金清点、终端支付结果核对仍由人承担。

课程提到业务蓝图需要甲方确认。因此本轮图表的准确名称是「依据当前合同整理的业务蓝图」，不能写成已经企业签字批准的流程。

## 3. B：需求获取与需求描述

### 3.1 需求获取方法在本项目中的适用方式

| 方法 | 适合解决的问题 | 优点与局限 | 本轮使用情况 |
|---|---|---|---|
| 资料研究 | 案例边界、既有实体、接口、业务规则 | 易取得、可追溯；历史文档可能落后于代码 | 已使用仓库和用户资料，冲突时记录差异 |
| 访谈 / 实地调研 | 实物交接、异常收款、关班责任、退款审批 | 能还原真实流程；受样本和记忆影响 | 未实施，不能以角色画像代替访谈证据 |
| 竞争产品研究 | 订单、退款、库存、支付结构参考 | 提供成熟拆分方式；产品规模和行业不同 | 两份 ERD 只作为模型表达和结构参考 |
| 问卷 | 任务频率、易错点、设备与网络条件 | 可量化偏好；难揭示深层原因 | 未实施，后续可在实际使用者中验证 |
| 亲自操作 | 按钮反馈、跳转、错误处理、任务连续性 | 能发现当前系统具体障碍；不代表真实经营结果 | 以本轮实际浏览器 / API 验证记录为准 |

需求平衡应体现在规约中：销售顾问需要快速录入，经营者需要核价与审计，因此保留草稿灵活性，但准备收款后使用快照和库存占用；顾客需要及时退款，经营者需要防止超退，因此退款与原销售行绑定，并保留原单。

### 3.2 用例规约的统一合同

每份规约包含编号、名称、执行者、涉众利益、触发、可检测前后置条件、主流程、扩展、字段、业务规则、质量要求和设计约束。以下五份是对现有 UC 编号的跨步骤细化：CR-SALE 对应 UC-05—08；CR-RETURN 对应 UC-09；CR-TRANSFER 对应 UC-04；CR-COMMISSION 对应 UC-10；CR-CLOSE 对应 UC-01 与 UC-03，不创建新的 UC-14 等编号。

共同合同：写操作要求有效身份、权限、CSRF 与 UUID 幂等键；相同操作者、操作名、幂等键和请求内容重试返回已记录响应，不重复写入；同键异体拒绝。数据库事务失败整体回滚，业务与审计同事务。金额输入为 CAD 十进制字符串，内部以整数分 `bigint` 计算，费率为 bps；金额输出通常是整数分字符串。字段长度与枚举以下以当前服务端和迁移为准。

### 3.3 CR-SALE：完成一笔现场销售

| 项目 | 规约 |
|---|---|
| 对应编号 / 级别 | UC-05 草稿、UC-06 准备收款、UC-07 确认成交、UC-08 取消核对；用户目标级 |
| 主要执行者 | SALESPERSON；OWNER 可代办、核对例外 |
| 涉众利益 | 顾客得到正确金额；销售顾问归属和佣金正确；经营者防止低价、超卖、重复登记 |
| 触发 | 顾客选定商品并接受现场议价 |
| 前置条件 | 账户有效；销售顾问只能操作本人班次；活动 OPEN、班次 ACTIVE 且当前时刻在计划时段内；准备收款时税率、佣金率及活动政策已配置；展位库存位置有效 |
| 成功后置条件 | 销售 POSTED 并生成 FX 单号；占用 CONSUMED；在手量和占用量同步减少；销售库存流水与非零佣金流水存在；记录收款方式、参考号 / 实收、操作者、时间和审计 |
| 最小保证 | 验证失败不形成半笔过账；DRAFT 不占用库存；CHECKOUT 中已占用的库存不得因浏览器关闭而无声消失 |

主流程：①选择有效班次，输入 1—100 行互不重复商品、数量和协商价；②服务端创建 DRAFT，返回 ID 与 version；③执行准备收款，携带当前 version；④服务端重新核对时段、政策、商品有效性、现行底价和可售库存；⑤对各行计算净额、税额和佣金，固化商品名、SKU、成本、底价、税率和佣金率快照，创建库存占用，单据进入 CHECKOUT；⑥顾客在线下付款；⑦操作人确认实际结果，提交现金实收或终端参考号；⑧服务端在同一事务中消费占用、扣库存、写流水与佣金、登记 POSTED 和审计；⑨界面显示单号、总额与现金找零。

| 扩展点 | 条件与处理 |
|---|---|
| ① 商品重复 / 数量或金额非法 | 返回输入错误；合并相同商品数量后再提交 |
| ③ 版本已变或不再 DRAFT | 返回冲突；刷新单据并重新确认，不覆盖他人修改 |
| ④ 班次过期、商品停用、底价上调、库存不足、政策未确认 | 准备失败且事务回滚；保留草稿供修正。0 税率 / 0 佣金率是合法配置，null 才表示未配置 |
| ⑦ 现金不足 / 终端参考号缺失 | 拒绝过账；实际资金状态不由系统猜测 |
| ⑦ 已到计划结束时刻但班次尚 ACTIVE | 现有准备好的 CHECKOUT 允许登记，前提是班次未关闭；不可把「禁止新建」误写成「禁止核对已收款」 |
| ⑧ 网络超时 | 保持原幂等键重试或查单；先确认服务器结果，不能用新键盲目重新创建交易 |
| 草稿取消 | 本人销售顾问或 OWNER 提供原因，转 CANCELLED |
| CHECKOUT 取消 | 仅 OWNER；必须确认 `paymentReconciled=true` 且 `goodsRecovered=true`，释放占用后转 CANCELLED |
| 已成交错误 | 不允许直接取消 POSTED，使用退货更正链保留原单 |

| 关键字段 | 类型 / 限制 / 含义 |
|---|---|
| shiftId、productId | 稳定正整数 ID，以字符串传输；归属以服务端查询为准 |
| lines | 1—100 行；每行商品不能重复 |
| quantity | 整数 1—9999 |
| finalUnitPrice | 非负金额字符串，最多两位小数；准备时须 ≥ 当前最低价 |
| version | 草稿修改和准备的乐观版本 |
| paymentMethod | CASH 或 TERMINAL |
| paymentReference | 有值时 1—120 字符；TERMINAL 必填 |
| cashReceived | CASH 必填且 ≥ 单据总额；找零为实收减总额 |
| reason / reconciliation flags | 取消原因 1—500 字符；CHECKOUT 需核对布尔确认 |

业务规则：可售量 = on_hand − reserved；草稿只录意向，准备后按快照成交；佣金以未税净额按快照 bps 计提；税额和佣金按行 half-up 舍入；零佣金不写零额流水；单据上限按服务端现有限制执行。质量要求：金额和库存强一致、重复确认不重复过账、销售顾问响应不含成本字段、请求中/成功/错误状态可见。建议性能验收为约定测试规模下单次操作 p95 ≤2 秒，这只是待测目标。设计约束：同源 API + Cookie 会话，MariaDB 单事务，不调用支付网关。

### 3.4 CR-RETURN：基于原销售办理退货和退款登记

| 项目 | 规约 |
|---|---|
| 对应编号 / 执行者 | UC-09；OWNER；顾客线下参与 |
| 涉众利益 | 顾客退款准确；经营者防止超退和损坏品误入可售库存；销售顾问佣金按原单冲回 |
| 触发 | 顾客提出退货并可定位原成交单 |
| 前置条件 | 原销售 POSTED；存在原销售行；目标为有效 MAIN，或原销售活动中仍 OPEN 的有效展位与库位 |
| 成功后置条件 | 退货 POSTED；原销售保持原状；RESTOCK 行增加目标在手和退货流水；DAMAGED 行不增加可售库存；非零佣金冲回；保留退款参考号和审计 |
| 最小保证 | 未授权不允许退款过账；失败不产生部分入库或部分佣金冲回 |

主流程：①管理员定位原销售并核对原行、已退量与本次实物；②建立退货 DRAFT，注明原因、目标库位、行数量和 RESTOCK / DAMAGED；③申请授权；④服务端锁定相关活动、原销售和退货，重新校验目标和剩余可退数量，保证同一原销售最多一个 AUTHORIZED 退货；⑤按原成交快照计算退款及佣金冲回，进入 AUTHORIZED；⑥管理员在线下完成退款并保留凭据；⑦提交 refundReference；⑧服务端重新核验目标，按商品加锁，只对 RESTOCK 回库，写非零负佣金，进入 POSTED 并审计。

| 扩展点 | 条件与处理 |
|---|---|
| ① 原单未成交或原行不存在 | 拒绝创建，不能用新退货伪造销售历史 |
| ② 超量草稿 | 当前创建入口录入草稿，正式剩余量校验在授权阶段；UI 可提前提示，但不能替代服务端校验 |
| ④ 累计已退 + 本次 > 原售数量 | 授权失败；按原行剩余可退量修正 |
| ④ 存在另一 AUTHORIZED 退货 | 先完成或受控取消旧授权，避免并行授权超退 |
| ④ / ⑧ 目标活动关闭、库位停用或跨活动 | 拒绝推进；不能把货退入其他活动展位。原活动关闭后仍可按规则退回有效 MAIN |
| ⑤ 分次退货出现舍入尾差 | 使用「累计应退额 − 已退额」计算本次税和佣金，全部退完时回到原额 |
| 取消 DRAFT | OWNER 提供原因，可取消 |
| 取消 AUTHORIZED | 必须确认 `refundReconciled=true`（实际退款尚未发生或已撤销）；不能为了清单干净而虚假勾选 |
| ⑦ 已退款但请求超时 | 复用原幂等键 / 查询结果；不能再次执行线下退款 |

| 关键字段 | 类型 / 限制 / 含义 |
|---|---|
| saleId、destinationLocationId | 必填正整数 ID；即使全是 DAMAGED，当前 API 仍要求合法目标 |
| reason | 1—500 字符 |
| lines | 1—100 行；saleLineNo 1—100 且同一原行不重复 |
| quantity / disposition | 正整数，默认上限 9999；RESTOCK 或 DAMAGED |
| refundReference | 过账必填，1—120 字符 |
| refundReconciled | 授权后取消必需的真实线下核对确认 |

业务规则：退款取原成交单价和原税额，佣金取原佣金快照；原单不可改写；目标在创建、授权和过账三阶段检查。质量要求：无超退、无重复退款登记、税额和佣金无累计尾差、异常说明指向处理动作。设计约束：退款仍由线下渠道执行；当前没有独立损坏品库、维修单和报废审批，DAMAGED 只保留退货行处置证据，应与未来损坏品管理区分。

### 3.5 CR-TRANSFER：登记已经完成实物交接的库存调拨

| 项目 | 规约 |
|---|---|
| 对应编号 / 执行者 | UC-04；OWNER |
| 涉众利益 | 经营者知道商品当前位置；销售顾问只能出售本展位可售库存；交接记录能追责 |
| 触发 | 主仓与展位、或有效库位之间完成实物交接后登记 |
| 前置条件 | 来源与目标不同且有效；关联活动非 CLOSED / CANCELLED；来源可售库存足够；交接确认真实 |
| 成功后置条件 | 来源在手减少 q，目标在手增加 q；生成一张 TRANSFER 单据、一行明细、相反符号的两条库存流水与审计；总在手量守恒 |
| 最小保证 | 任一校验或写入失败，来源和目标都不变化 |

主流程：①选择商品、来源库位、目标库位、数量并填原因；②核对已完成的实物交接并勾选确认；③提交命令；④服务端按 ID 顺序锁涉及活动、商品与库位余额；⑤验证来源扣减后仍不小于 reserved；⑥同事务扣来源、加目标、写单据及双向流水；⑦返回单据 ID 并刷新相关库存。

| 扩展点 | 条件与处理 |
|---|---|
| ① 来源 = 目标 | 输入错误，必须修改 |
| ② 未确认实物交接 | 拒绝；本用例不负责发运或接收在途商品 |
| ④ 活动已关闭或库位失效 | 冲突；先核对实际去向，不绕过闭场规则 |
| ⑤ 在手足够但已有销售占用 | 按可售量拒绝调拨；先处理对应待成交单，不挤占顾客已准备收款的库存 |
| ⑥ 竞争写入或死锁 | 事务回滚并按既有有限重试机制处理；持续失败需重新查询余额 |
| ⑦ 响应丢失 | 复用幂等键，避免双扣双增 |

| 关键字段 | 类型 / 限制 / 含义 |
|---|---|
| productId、fromLocationId、toLocationId | 正整数 ID 字符串；来源和目标不同 |
| quantity | 整数 1—1,000,000 |
| reason | 1—500 字符 |
| handoverConfirmed | 必须为 true；是人工确认，不是第二名接收人的独立签收 |

业务规则：每次 API 调拨一款商品；两端变化同事务；不得使 on_hand < reserved。质量要求：库存守恒、可追溯、重复提交不重复移动、页面明确来源 / 目标 / 可售量。设计约束：当前是单阶段原子登记，没有 TRANSFER 单据状态、在途库存、发货人 / 收货人二次确认。图上不得画出不存在的 DISPATCHED、IN_TRANSIT、RECEIVED 状态。多商品批次交接与双人签收属于未来需求，需要新增规约及事务设计后再实现。

### 3.6 CR-COMMISSION：核对佣金并登记线下支付

| 项目 | 规约 |
|---|---|
| 对应编号 / 执行者 | UC-10；OWNER；销售顾问可查看本人记录 |
| 涉众利益 | 顾问知道收入来源；经营者不会重复结算，退货负项可抵扣 |
| 触发 | 到约定的线下结算时间，管理员请求准备某员工结算 |
| 前置条件 | 员工存在；该员工没有 PREPARED 结算；未被认领的佣金正负流水合计 >0 |
| 成功后置条件 | 结算 PAID；结算明细和认领保留；支付参考号、支付时间与审计可查；之后产生的退货负项留待后续结算 |
| 最小保证 | 余额非正不生成可支付结算；同一流水不能同时认领到两个结算 |

主流程：①管理员选择员工并核对销售正佣金和退货负佣金；②提交准备命令；③服务端锁员工，检查无待核对结算，选择全部尚未认领流水并加锁；④净额为正时创建 PREPARED、结算明细及 commission_claims；⑤管理员线下支付；⑥提交 paymentReference；⑦服务端仅将 PREPARED 转 PAID，保存凭据、时间与审计；⑧员工查看本人结算结果。

| 扩展点 | 条件与处理 |
|---|---|
| ③ 已有 PREPARED | 返回冲突；先核对旧单，不生成第二张待付单 |
| ④ 未结净额 ≤0 | 拒绝准备，不创建负数支付；退货负项继续保留 |
| ④ / ⑦ 并发或重试 | 员工锁、流水认领唯一性与幂等共同防重；仍需真实并发验收 |
| ⑤ 尚未支付或支付已撤销 | OWNER 提供原因并确认 `paymentReconciled=true`，取消 PREPARED 并释放认领 |
| ⑦ 结算已 PAID / CANCELLED | 不再允许支付登记；已付单不靠修改金额来抵扣后来的退货 |
| 已结算后发生退货 | 新负佣金流水进入之后结算，不改写原已付结算 |

| 关键字段 | 类型 / 限制 / 含义 |
|---|---|
| salespersonId | 准备时必填；当前 API 不接受自选日期范围 |
| cutoff_at | 准备时服务器时间，用于记录结算时点；实际认领集合由当次锁定的未认领流水决定 |
| total_cents | 有符号金额合计；新结算必须 >0 |
| paymentReference | 付款登记必填，1—120 字符 |
| reason / paymentReconciled | 取消原因 1—500 字符，且必须确认线下付款未发生或已撤销 |

业务规则：commission_entries 是正负事实流水；commission_settlement_lines 保留结算快照；commission_claims 的 entry_id 主键保证一条流水只有一个当前认领。取消释放认领但保留取消结算与明细。佣金率修改只影响之后 sale.prepare 的快照。质量要求：不重复支付登记、口径可解释、本人访问隔离、失败不丢认领。设计约束：没有银行自动付款、支付回调或自动对账；准备结算不等于付款成功。

### 3.7 CR-CLOSE：核对阻塞事项并关闭活动

| 项目 | 规约 |
|---|---|
| 对应编号 / 执行者 | UC-01 活动管理，与 UC-03 班次管理协作；OWNER |
| 涉众利益 | 经营者得到完整闭场事实；销售顾问未结单有处理出口；顾客已付款 / 已退货事实不会被关闭操作掩盖 |
| 触发 | 活动经营结束，管理员准备封闭现场交易 |
| 前置条件 | 活动存在且 OPEN；无 PLANNED / ACTIVE 班次；无 DRAFT / CHECKOUT 销售；该活动展位无正数在手库存；无已授权且含 RESTOCK 行的待入本活动展位退货 |
| 成功后置条件 | 活动 CLOSED，version 增加，写 EVENT_CLOSED 审计；历史销售、退货与报表仍可查询 |
| 最小保证 | 任何阻塞事项存在都不改变活动状态，不自动取消单据、不抹掉库存 |

主流程：①管理员查看活动待办并定位尚未处理班次、销售、库存和退货；②完成或受控取消待成交单；③关闭已 ACTIVE 班次；从未开班且无任何销售关联的 PLANNED 班次可依规取消；④实物退回主仓后登记调拨，或按真实盘点差额登记调整；⑤处理会回库至本活动展位的授权退货；⑥提交闭场；⑦服务端锁活动并重新查询四类阻塞事项；⑧全部清零才转 CLOSED。

| 扩展点 | 条件与处理 |
|---|---|
| ② 已付款未登记 / CHECKOUT | 先核对线下收款和商品事实，过账或受控取消，不能直接释放占用 |
| ③ PLANNED 已过期但未开班 | 现有取消入口允许 OWNER 提供原因与版本取消；若有实际开始 / 结束或任意销售关联则拒绝 |
| ③ ACTIVE 仍有 DRAFT / CHECKOUT | 关班拒绝，先处理销售 |
| ④ 剩余库存 / 占用 | 先实物交接和登记；盘点不允许把库存降到占用以下 |
| ⑤ 待入展位授权退货 | 完成真实退款和入库，或在真实线下条件满足时受控取消 |
| ⑦ 同时发生销售 / 调拨 / 退货 | 共享活动锁串行化重要检查；闭场重新验证，仍需竞争场景测试 |
| ⑦ 已 CLOSED 或非 OPEN | 返回冲突；当前没有重开活动接口 |

关键字段：路径 `eventId`、请求 Idempotency-Key；闭场当前 API 无版本 / 原因请求体，version 由服务端增加。若界面设计「闭场说明」，不能假定服务器已保存该字段。业务规则：目标是现场闭场，不要求所有佣金已经 PAID，也不要求所有退回 MAIN 的售后单结束；禁止把两种口径混为一谈。质量要求：阻塞原因应可定位，修复后可继续操作，拒绝关闭时数据不变。设计约束：现有服务端冲突信息是汇总提示；按项返回数量、对象 ID 和前往处理入口属于建议补强，除非本轮另有明确实现证据。

## 4. C：分析模型如何从需求推导

### 4.1 类图：概念、属性、操作和关系

从销售规约的名词识别 Sale、SaleLine、Product、Shift、Salesperson、Event、Booth、StockBalance、StockHold；从退货和佣金事件补充 Return、ReturnLine、CommissionEntry、CommissionSettlement。类图中的操作由动词推导，如 Sale.prepare / post / cancel、Return.authorize / post / cancel、Settlement.prepare / pay / cancel。

这些是分析层职责名称，当前 TypeScript 主要是函数与数据库行接口，没有同名的富领域实体类。因此类图标题应写「领域分析类图」，不能画完就宣称仓库已经按每个类实现了方法。

| 关系 | 本项目可据实表达的例子 | 语义限制 |
|---|---|---|
| 一对多关联 | Venue—Event、Event—Booth、Salesperson—Shift、Shift—Sale、Product—SaleLine | 标明最小 / 最大基数；一个新活动可以暂时没有展位，但开放时需要展位 |
| 组合 | Sale—SaleLine、Return—ReturnLine、Settlement—SettlementLine | 说明业务生命周期从属；SQL 不使用级联删除也不否定业务组合，历史单据不能随意删 |
| 关联类 / 多对多 | Product 与 StockLocation 由 StockBalance 关联；Sale 与 Product 由带数量 / 单价的 SaleLine 关联 | 中间实体具有业务属性，不只是无意义连接表 |
| 角色而非继承 | OWNER、SALESPERSON 是 users.role 枚举和关联约束 | 无需强造 Owner extends User、Salesperson extends User 的现有代码结构 |
| 无现有自反关系 | 课程里的商品分类树和科目父子关系是参考模式 | 当前 products / event_categories 不含 parent_id，不能在当前物理 ERD 中凭空画出来 |

概念模型可保持案例核心实体简洁；物理模型必须包含库存、权限、幂等和审计等实现辅助表。两张图服务不同读者，不应强行变成完全相同的实体数。

### 4.2 序列图：边界、控制、实体协作

系统序列图应以真实 HTTP 命令为边界。以准备收款为例：销售页面（boundary）→ API / 命令处理器（control）→ 会话 / 权限校验 → command 幂等检查 → Event / Sale / Product / StockBalance 加锁 → 写 StockHold 和 SaleLine 快照 → Sale 更新 CHECKOUT → audit → COMMIT → 返回总额。异常通过 alt 片段表示版本冲突、缺库存、低于底价和重复命令；事务用明确框标识，不把线下支付画进数据库事务。

建议五条核心图和上述五份规约一一对应；其他 UC 至少有模块调用与合同追踪。外部现金 / 终端的真实动作发生在两次 API 调用之间，因此必须体现「系统无法自动知道资金结果」的人工核对步骤。

### 4.3 状态图：必须对应枚举与守卫条件

| 对象 | 当前状态与主要转换 | 不应画成已实现的转换 |
|---|---|---|
| Sale | DRAFT → CHECKOUT → POSTED；DRAFT / CHECKOUT → CANCELLED | POSTED → DRAFT；付款失败后自动清空占用 |
| Return | DRAFT → AUTHORIZED → POSTED；DRAFT / AUTHORIZED → CANCELLED | POSTED → DRAFT；未授权直接入账 |
| Shift | PLANNED → ACTIVE → CLOSED；满足守卫的 PLANNED → CANCELLED | CLOSED → ACTIVE；带销售历史的计划班次任意取消 |
| Event | DRAFT → OPEN → CLOSED；数据库还定义 CANCELLED | 未找到活动取消接口时，不应把 DRAFT → CANCELLED 标成当前可操作流程 |
| StockHold | ACTIVE → CONSUMED 或 RELEASED | 自动超时释放；当前没有自动过期任务 |
| CommissionSettlement | PREPARED → PAID 或 CANCELLED | PAID 后直接改金额或撤销历史 |
| StockDocument | kind 区分 RECEIVE / TRANSFER / ADJUST / RETURN | 没有状态字段，不应编造在途调拨状态机 |

状态图不仅画箭头，还要标注执行者、守卫和关键副作用。例如 CHECKOUT → CANCELLED 的守卫是 OWNER + 资金已核对 + 商品未交付或已收回，副作用是释放 ACTIVE 占用。

## 5. D：设计模型如何落实到数据库、业务代码和界面

### 5.1 数据库层：以实际迁移为准

当前 `001_core.sql` 实际创建 **25 张应用表**，迁移脚本另外创建 `schema_migrations`，合计 **26 张表**。旧 README 的「24 张业务表 + 1 张迁移表」不符合迁移数量，不能沿用为新图标题。

| 子域 | 当前物理表 |
|---|---|
| 场地与活动 | event_categories、venues、events、booths |
| 人员、班次、身份 | salespeople、shifts、users、sessions |
| 商品与销售 | products、sales、sale_lines |
| 库存 | stock_locations、stock_balances、stock_documents、stock_document_lines、stock_ledger、stock_holds |
| 售后 | returns、return_lines |
| 佣金 | commission_entries、commission_settlements、commission_settlement_lines、commission_claims |
| 横切记录 | idempotency_keys、audit_events |
| 迁移版本 | schema_migrations，技术表单独标注 |

PK、FK、唯一键和业务约束应分开说明。主键标识不能随商品改名、活动改名或列表排序变化。sku、username、sale_no 是具有各自业务含义的唯一键，不应全部替代内部 ID。

| 课程设计点 | 当前实现例子 | 评审含义 |
|---|---|---|
| 1:n，外键在 n 方 | events.venue_id；booths.event_id；sale_lines.product_id | 可以通过 FK 禁止引用不存在的实体 |
| 复合归属 | booths(id,event_id) 被 shifts(booth_id,event_id) 引用；shifts(id,event_id) 被 sales 引用 | 保证展位、班次、销售的活动归属一致，不只靠前端选择器 |
| m:n 中间表 | stock_balances(location_id,product_id)；sale_lines(sale_id,line_no) 同时关联商品；结算明细关联结算与佣金流水 | 表内保存数量、金额和业务身份；commission_claims 额外限制当前认领唯一 |
| 组合主键 | sale_lines(sale_id,line_no)、stock_holds(sale_id,line_no)、stock_balances(location_id,product_id) | 必须在图中明确全部 PK 成员，不能只画一个 id |
| 自反关系 | 当前应用表未定义父子自反 FK | 课程参考的 category.parent_id、account.parent_id 仅作为未来需求示例 |
| 值表 | event_categories 七个种子类别 | 它是被 events 引用的字典表，不是独立的业务交易 |
| 枚举和检查 | on_hand≥reserved、数量正、费率≤10000、角色与 salesperson_id 配对 | 应标注类型、NULL、CHECK；图中一个字段名不能替代这些规则 |
| 金额和快照 | BIGINT 分；成交行保存成本 / 底价 / 税率 / 佣金率 / 名称 / SKU | 历史结果不因主数据变化重新计算 |

并非所有业务关联都有数据库外键。`stock_ledger(source_kind,source_id,source_line_no)` 和 `commission_entries` 的来源是多态关联；`return_lines.sale_line_no` 通过父退货的 sale_id 定位原行，当前没有直接的原销售行复合 FK；审计 subject_type / subject_id 同样是逻辑指向。因此物理 ERD 要用不同线型区分「已建 FK」和「应用维护的逻辑关系」，并在字典中说明校验责任与不变量检查，不能把虚线画成已有强外键。

类到表不是机械一对一。Sale 聚合拆为 sales / sale_lines / stock_holds 等；money 可作为值对象而落成 BIGINT；用户角色当前是单表枚举。若未来出现真正的泛化，可比较单表继承（查询简单、空字段较多）、类表继承（结构清晰、需联接）、具体类表（重复公共字段、跨类统计复杂），但本项目没有必要为了课程名词而改造为继承层次。

### 5.2 数据访问模式与 DDD 的实际落点

当前实现是 Fastify 路由函数内组织业务事务，调用 `mysql2` 和 `rows / first / exec / tx` 辅助函数。它接近按用例组织的事务脚本，已有模块文件、少量纯规则提取和统一事务设施；它既不是 Active Record ORM，也不是已完整实现的 Data Mapper / Repository 富领域模型。

课程提到的 Table Data Gateway、Row Data Gateway、Active Record / 数据对象、Data Mapper 可作为方案比较：前两者围绕表或行封装访问；Active Record 让对象同时知道持久化；Data Mapper 将领域对象和持久化隔开。当前公共 SQL 工具主要提供连接与执行能力，不足以据此宣布存在独立数据映射层。

建议渐进式提取：把金额 / 可退量 / 状态守卫保留为纯函数，把一次业务命令组织为 application service，把 SQL 封装为针对聚合的 repository。业务逻辑负责「什么时候可以过账」，数据访问负责「如何锁定和保存」。保持当前事务边界、锁序、幂等和快照不变后再重构，不为教学展示一次性拆成微服务。

可划分的领域职责是现场销售、库存、售后、佣金、活动排班，身份与审计为支撑能力。它们当前部署在同一个单体中，跨模块共用数据库；所谓 DDD 在这里首先是统一术语和明确不变量，而非声称已经有事件总线、事件溯源、CQRS 或独立限界上下文部署。

### 5.3 表示层：用信息架构和状态反馈减少业务中断

前端是 React + TypeScript + Vite，经 Fastify 同源提供页面和 API。界面应围绕任务组织：准备活动 → 备货开班 → 现场销售 → 例外核对 → 日终闭场；管理员和销售顾问应看到各自可以操作的入口。

建议交互合同：销售显示「草稿 / 准备收款 / 已成交」三步与每步下一动作；库位选择显示名称、所属活动和可售量；退货显示原数量、已退量、剩余量与处置去向；佣金分开显示正项、负项、待付和已付；闭场显示阻塞事项及处理入口。按钮禁用应同时给出原因，成功后更新列表并保留可访问凭证，失败时保留用户已输入的内容。

视觉上采用一致的字号、间距、颜色和状态徽标，适度使用卡片、分组与过渡。动效只用于表达加载、提交和状态变化；移动设备不应因悬浮才出现关键操作；颜色不是唯一状态提示；`prefers-reduced-motion` 时减少非必要动画。UI 提前检查提升体验，但权限、金额、库存和状态守卫仍由服务器执行。

## 6. 两份规范 ERD 的借鉴与限制

Quickbooks 1.0 ERD 为 1 页，6120×3456 pt（85×48 英寸）；Shopify ERD 为 1 页，7236×3960 pt（100.5×55 英寸）。两者均有 Fivetran 标识，Shopify 图还包含 `_fivetran_deleted`、`fivetran_id`、PLUS 和弃用标记。因此应称为「Fivetran 对源系统数据的模型参考」，不能把它们直接当成 Foxcore 的商户业务数据库。

可借鉴的表达是：明确表头、PK/FK 图例、字段逐行排列、相近业务域分组、主单与明细分离、读图方向一致。QuickBooks 的 INVOICE / INVOICE_LINE / INVOICE_TAX_LINE、BUNDLE_ITEM 组合关系可帮助理解单据与连接表；Shopify 的 PRODUCT / PRODUCT_VARIANT / INVENTORY_ITEM / INVENTORY_LEVEL 分离，以及 ORDER、TRANSACTION、REFUND、FULFILLMENT 的不同生命周期可帮助判断零售功能边界。

不能照抄的内容是：巨幅画布上的全部字段、厂商同步字段、Plus 专有字段、弃用表、与项目无关的税务和会计全套结构。参考图的箭头也不完整表达基数、可选性和物理约束。新图应增加清晰基数、PK/FK/UK、类型和约束，必要时用多张分域图替代一张不可读的巨图。当前 Foxcore 没有商品变体或多渠道履约需求，就不必机械增加 Shopify 同名表。

## 7. 完整性审查与优先优化清单

总体判断：项目已有覆盖核心现场零售的完整骨架，销售—库存—退货—佣金的联动比单纯 CRUD 完善；尚不能把「文档很多、图很多、接口存在」等同于业务已经全面验证。优先补齐图文与代码一致性、关键任务可操作性和运行证据，再决定是否扩张业务范围。

| 优先级 | 已发现事实 / 缺口 | 建议与验收方式 |
|---|---|---|
| P1 | 旧文档表数 24+1 与实际 25+1 不符；部分旧图 / PDF 未同步 | 以迁移自动生成表清单，统一新图和数据字典；保留旧文件的版本提示 |
| P1 | SRS 把审计描述为数据库触发器，实际是应用显式同事务 INSERT | 纠正文案；检查所有关键写路由均调用 audit；运行权限验证审计不可任意修改 |
| P1 | 文档中存在旧 PASS 与修复后 NOT_RUN 并列 | 每轮形成独立环境、提交、命令、退出码和失败边界；不得合并成笼统“全部通过” |
| P1 | 闭场 API 只返回组合错误，现场不易定位阻塞 | 返回 / 展示四类阻塞计数和可处理对象，验证从失败提示能走完修复再闭场 |
| P1 | 资金动作在线下，CHECKOUT / AUTHORIZED / PREPARED 均可能长时间待核对 | 明确待办队列、责任人、真实核对与异常恢复说明；不能自动超时撤销真实资金 |
| P2 | 当前类图职责与函数 / 事务脚本实现容易被混淆 | 标注「分析类图」，维护服务函数映射；逐步提取纯规则和数据访问边界 |
| P2 | 多态来源和退货原行关联由应用维持，非全是 FK | 物理图分线型；补审计 / 不变量校验，评估未来是否增加冗余 sale_id 与复合 FK 的迁移成本 |
| P2 | 损坏品不进入可售库存，但没有独立损坏库存与后续处置 | 先确认业务是否需要维修 / 报废核销；需要时才扩展单据和库位，避免报表把损坏品视为凭空消失 |
| P2 | 同活动的命令共享活动锁；没有可信吞吐基准 | 以实际数据量和并发测 p95、锁等待和死锁重试；证据不足时不承诺高并发能力 |
| P2 | 原子调拨适合已完成交接，无法表达跨场地在途 | 保持当前文案准确；如业务需要在途与双人签收，单独设计数量占用、差异接收和撤销规则 |
| P2 | 10k 目录 / 导出边界与跨页变化会影响大规模使用 | 现阶段明确报错；增长后采用搜索选择器、游标和异步导出，并重新设计一致性口径 |
| P3 | 顾客会员、供应商采购、总账、在线支付等尚未实现 | 这是范围选择，不应直接判成核心缺陷；需要真实需求和投入收益后才扩展 |

## 8. 图表与规约交付索引

本课程最有价值的交付链是「愿景 → 业务用例与蓝图 → 系统用例规约 → 类 / 序列 / 状态模型 → ERD / 分层 / 界面 → 验证证据」。建议图册包含以下内容，并在图注标明当前实现或建议模型：

1. 涉众与系统上下文图；业务用例图。
2. AS-IS 业务序列图（标明案例来源 / 待验证假设）；TO-BE 业务序列图。
3. 系统用例图，保留 UC-01—UC-13，角色及直接交互边界准确。
4. 领域分析类图，列出属性、职责、基数和组合关系，不伪造现有代码继承。
5. 核心概念 ERD、完整物理 ERD及分域 ERD；25 张应用表与迁移表分别标注。
6. 现场销售、退货、调拨、佣金、闭场五组系统序列图。
7. 销售、退货、班次、活动、库存占用、佣金结算状态图。
8. 组件 / 分层图、部署拓扑图；当前单体架构与未来建议分开。
9. 页面导航与任务流、角色权限矩阵、字段字典、关键规则表。
10. 用例—代码—数据表—测试的追踪矩阵；每项状态用已运行通过、失败、阻塞、未运行表达。

至此，课程中的业务建模、需求、分析和设计都有对应产物；真正的完整性还要由可执行业务链及其证据闭环确认。
